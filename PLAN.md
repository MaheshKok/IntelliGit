# Plan: Visual + E2E testing on a dedicated fixture repository

_Locked via grill — by Claude + Mahesh, 2026-08-06. Revised across 5 Codex review rounds (57 findings dispositioned, 56 fixed); closed by owner arbitration at MAX_ROUNDS. See `PLAN-REVIEW-LOG.md`._

## Goal

Give IntelliGit two testing layers it does not have today, on top of the existing 168-file vitest suite:

- **Layer 1 — webview visual regression.** Headless Chromium renders the real built `dist/webview-*.js` bundles fed with **recorded** protocol payloads, and pixel-diffs them against committed baselines. Catches CSS/layout/theme regressions that jsdom structurally cannot see (jsdom has no layout engine).
- **Layer 2 — real VS Code E2E against a real git repository.** Playwright's `_electron` drives an actual VS Code build with `--extensionDevelopmentPath`, against a fixture repository **restored to a known initial state before every test by a contract-checked recursive copy, modulo declared live rewrites** (step 8), proving that mutating commands really mutate git and that the UI repaints correctly afterwards.

Both layers are underpinned by one seeded, deterministic fixture repository (working repo **and** a bare `origin`), and the harness code that builds and resets it is itself unit-tested — because a harness bug produces silent false-green, the single worst failure mode in a test suite.

Cypress is not a candidate: it runs only inside a browser and cannot drive VS Code, which is an Electron desktop application. Playwright drives Electron (`_electron.launch`), drives plain Chromium, and ships `toHaveScreenshot` pixel diffing — one runner covers both layers.

**Governing principle, added in v2:** every oracle in this system must be proven able to *fail*. An assertion that cannot go red for a known-bad input is worse than no assertion, because it converts an untested surface into a green checkmark. Phase 6 exists to enforce this.

## Approach

### Phase 0 — Spike: prove `_electron` can reach a webview, and capture the host fixtures

Before any infrastructure is written, settle the assumption the entire plan rests on.

1. Add dev deps: `@playwright/test`, `@vscode/test-electron`.
2. **Build first — and fix the build script, which currently defeats any existence-based gate.** `dist/` is git-ignored ([.gitignore:146](.gitignore:146)) and `package.json` `main` points at `dist/extension.js`, so every launch, spike, CI job, and harness-server start must be preceded by a verified build. An existence check is not sufficient, because [build.js:59-66](scripts/build.js:59) wraps each webview build in `try { … } catch { console.log("Skipped (not found)") }` — it **swallows genuine compile errors as if the entry were merely absent**, and nothing cleans `dist/`. A webview that fails to compile therefore leaves last build's stale bundle in place, satisfies the existence check, and both layers happily test old code (Codex R4 #1). This is a real pre-existing bug: it means a broken webview can ship. So:
    - `scripts/build.js` distinguishes "entry file does not exist" (skip, as intended) from "esbuild threw" (**fatal**), and declared outputs are cleaned or atomically replaced rather than left behind.
    - The gate then asserts not just presence but **provenance**: the extension bundle, the rebase editor helper, all 7 webview JS bundles, and the generated CSS must all be outputs *of that invocation*, verified by content hash recorded at build time.
3. `tests/e2e/spike/launch.spec.ts`:
    - `downloadAndUnzipVSCode(VSCODE_VERSION)` from `@vscode/test-electron` → absolute binary path.
    - `_electron.launch({ executablePath, args: ['--extensionDevelopmentPath=<repo>', '--disable-workspace-trust', '--skip-release-notes', '--disable-gpu', `--user-data-dir=${tmp}`, `--extensions-dir=${tmp}`, fixtureRepoPath], env: SANITIZED_GIT_ENV })`.
    - Open the IntelliGit view, resolve the webview via nested `frameLocator` (VS Code nests an outer `webview` iframe around an inner `active-frame`), assert `#root` has children.
4. **Capture the host fixture** — not just the CSS variables. `document.documentElement.style.cssText` alone is insufficient: [shikiHighlighter.ts:68](src/webviews/react/merge-editor/shikiHighlighter.ts:68) branches on `classList.contains("vscode-dark") || classList.contains("vscode-high-contrast")`. (An earlier draft also cited `theme.ts` here; that citation was **wrong** and is withdrawn — [theme.ts:9](src/webviews/react/shared/theme.ts:9) explicitly says lane colours are chosen "by measuring the resolved editor background rather than by reading the `vscode-dark` / `vscode-light` body class", precisely because custom themes carry a class that disagrees with what they paint. `shikiHighlighter.ts:68` is the verified body-class consumer, and one consumer is enough to make the class list load-bearing — Codex R4 #10.) A fixture missing the class list renders light syntax colours inside a dark baseline and the diff still passes. So one **host fixture** records, as a single versioned artifact:
    - root element `style.cssText` (the `--vscode-*` custom properties),
    - `documentElement` and `body` **class lists**,
    - `documentElement` and `body` **datasets** (`data-vscode-theme-kind`, `data-vscode-theme-id`, …),
    - provenance: VS Code version **and commit**, platform, theme ID, theme kind, and a capture-schema version.
5. Capture runs once per theme, **each in a fresh profile with an explicitly selected built-in theme ID** — never "whatever theme happened to be active". Four fixtures: `dark-modern`, `light-modern`, `hc-black`, `hc-light`. The two high-contrast fixtures are required because Phase 3's non-pixel high-contrast assertions have nothing to assert against without them.
6. **Gate:** if steps 3–5 do not work on macOS local *and* in the pinned Linux container, stop and re-plan. Freshness of the captured fixtures is enforced by **recapture-and-compare, not by provenance** (see step 39) — provenance metadata can be perfectly valid while the CSS variables, classes, or datasets beside it are wrong.

### Phase 1 — The fixture repository: seed → template → **contract-checked copy** per test

> **v2 change (Codex #1, CRITICAL).** The original plan used `git clone --local` per test. `git clone` copies **only reachable committed objects and a checkout** — it does not carry untracked files, ignored files, index/staging state, `.git/config`, reflogs, `refs/stash`, or in-progress sequencer state. Every one of those is seeded state this suite depends on, so a "discard changes" or "stash pop" test would have started with nothing to act on and **passed vacuously**. Rather than hydrate a clone back to correctness (patching the symptom), the restore primitive is a **contract-checked recursive copy of the whole template**, equivalent to it modulo a declared set of live path rewrites (step 8) — which eliminates the defect class instead of compensating for it.

7. `tests/fixtures/repo/seed.ts` exports `seedFixtureTemplate(destination)`, building a repository whose state exercises the mutating command surface:
    - **Sanitized git environment for every git process**, not just the seed's: `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, a scratch `HOME`, fixed `GIT_AUTHOR_*`/`GIT_COMMITTER_*` identity and dates. This is the technique at [rebaseTestHarness.ts:26](tests/integration/rebase/rebaseTestHarness.ts:26), extended past the seed: the **extension's own** git subprocesses and the Phase 2 recorder must inherit it too, or commits created *during* a test pick up ambient time and user config and the resulting SHAs drift per machine (Codex #8).
    - Repo config pinned: `core.autocrlf=false`, `core.ignorecase=false`, `init.defaultBranch=main`, `gc.auto=0`, `commit.gpgsign=false`, fixed `core.abbrev`.
    - History: linear `main`; a `feature/*` branch ahead 3 / behind 2; a branch conflicting with `main`; a merge commit; a multi-lane region for graph lane colouring; a tag.
    - Dirty layer (the part a clone would have destroyed): an ignored file, an untracked file, a staged-and-unstaged file, a binary file, a CRLF file, a renamed file, pre-seeded stash entries.
    - A **bare repository as `origin`**, with `file://` remotes and upstream tracking, so push / pull / fetch / publish-branch / force-push-with-lease / ahead-behind have a real other side.
8. `tests/fixtures/repo/harness.ts` exports `createFixtureWorkspace()`. The copy is **not** "byte-exact by construction" — that was an overclaim, since a recursive copy has no inherent contract for symlinks, modes, timestamps, or inode separation, and the origin-URL rewrite deliberately changes copied bytes (Codex R2 #6). The contract is therefore stated and asserted:
    - Template built **once per run**, in a Playwright **setup project** that every test project declares as a `dependencies` entry, with a matching teardown project. A module-scoped memoized promise would be wrong (Codex R4 #8): module scope is **per worker process**, and Playwright runs workers concurrently and restarts them after a crashed test — so "once per suite", the single `fsck`, and the single template root would all silently become "once per worker, sometimes twice". The setup project runs exactly once regardless of worker count. It publishes the template path through an **atomic per-run manifest file at a runner-known path** (written to a temp name, then renamed), *not* through the environment (Codex R5 #6): a setup project runs in **its own worker process**, so mutating `process.env` there is invisible to every other worker — the publication mechanism would have silently produced workers that each rebuilt their own template, defeating the fix. Workers read the manifest; a missing or partial manifest is a hard failure, never a silent rebuild.
    - Copier options are pinned explicitly: `recursive`, `force`, `preserveTimestamps: true`, `dereference: false`, `verbatimSymlinks: true` — so symlinks are copied as links with their literal targets rather than being resolved into the copy.
    - **Two distinct operations, not one (Codex R3 #5).** *Live rehydration* rewrites metadata on disk to **concrete per-test absolute paths** — the copy's `origin` URL, and any absolute template path in copied config or worktree metadata. A repository containing the literal string `<ROOT>` would not function. *Normalization* is comparison-only: when producing an inventory or diff, those concrete paths are mapped to the canonical placeholders `<ROOT>`, `<ORIGIN>`, `<PROFILE>` so two workspaces at different paths compare equal. Placeholders never touch the filesystem.
    - **Equivalent to the template modulo the declared rewrite set**, and nothing else: after rehydration, a normalized diff against the template must show *only* declared rewrites.
    - A copy inventory records, per entry: type (file/dir/symlink/special), mode, symlink target text, and content digest. **No regular file in a copy may share an inode with the template** — asserted, because a hardlinked copy lets one test's mutation corrupt every other.
    - **Symlink containment (Codex R3 #6).** `verbatimSymlinks: true` faithfully preserves a link whose target is absolute or escapes upward — which means a copied link can still resolve into the template or elsewhere outside the copy, passing both the inventory and the diff while writes through it corrupt shared state. Therefore: every symlink's resolved target must land inside the declared roots (`<ROOT>`, `<ORIGIN>`, `<PROFILE>`); a template-contained absolute target is rebased onto the copy; anything else is rejected at copy time. A test writes through a copied link and asserts the template is unchanged.
    - Case-insensitive filesystems (macOS default) are covered by the inventory comparison, which is case-sensitive on recorded names.
    - Returns `{ root, originRoot, profileDir, dispose }`. Reset is `dispose()` + a fresh copy — never in-place undo.
9. **Canonical snapshot.** `snapshotWorkspace()` captures the full restorable domain, and the initial snapshot is the oracle Phase 6 asserts against. It covers, for **both** the workspace and the bare origin:
    - Working tree: tracked + untracked + **ignored** files, with type/mode/symlink-target/digest per entry.
    - Index, including **flags and unmerged stages** (not merely `ls-files`).
    - **All refs enumerated exhaustively** (`for-each-ref` over the full namespace, not just branches/tags/remotes), plus `HEAD`, `refs/stash`, and all reflogs.
    - `.git/config`, `FETCH_HEAD`, `ORIG_HEAD`, `REBASE_HEAD`, `AUTO_MERGE`, `MERGE_HEAD`/`CHERRY_PICK_HEAD`/`REVERT_HEAD`, `MERGE_MSG`/`SQUASH_MSG`, `sequencer/`, `rebase-merge/`, `rebase-apply/`, rerere data, `$GIT_COMMON_DIR/intelligit/*`.
    - **Per-worktree and common-directory private state — inventoried recursively, with a documented exclusion list rather than a hand-written include list** (Codex R3 #4). Naming individual files guarantees omissions: the earlier list already missed `commondir`, `config.worktree`, per-worktree `FETCH_HEAD`, `COMMIT_EDITMSG`, and per-worktree logs. So every resolved worktree git directory *and* the common directory are walked recursively, and only explicitly documented paths are excluded. This is not optional trivia for this extension: [executor.ts:105](src/git/executor.ts:105) and [repositoryMutationGate.ts:14](src/git/repositoryMutationGate.ts:14) do common-dir–scoped locking, so worktree admin state is load-bearing behaviour under test. Linked worktree *directories* live **outside** the repo root, so `dispose()` enumerates and removes them rather than just deleting the root.
    - **`BISECT_*` state**, which the recursive walk covers and which is specifically load-bearing here: [guards.ts:100](src/git/interactiveRebase/guards.ts:100) probes `git bisect log` by exit status to refuse starting a rebase mid-bisect, so a leaked bisect session silently changes rebase behaviour in a later test.
    - **Object-store integrity**: an object inventory, and an assertion that `objects/info/alternates` is either absent or points only inside the copy — an alternates file still pointing at the template would make copies silently share objects.
    - Durable VS Code state (see step 10).
    - Anything deliberately excluded carries a written rationale in the code.
    - **`git fsck` scope (partial reject of Codex R2 #3).** `fsck` runs on the template once per suite and inside the Phase 6 harness tests — not on every per-test copy. Per-test `fsck` on hundreds of copies buys corruption detection that the inventory + digest comparison already provides, at a per-test cost this suite cannot absorb.
10. **Extension-side durable state resets too, and is addressable.** Three distinct stores, all named explicitly (Codex R2 #5):
    - **`globalStorageUri` files** — shelf entries and interactive-rebase manifests. These are keyed by a hash of the repository's real path: [paths.ts:31](src/shelf/paths.ts:31) does `realpath` → sha256 → repoId. A shelf seeded into the *template* is therefore unreachable once the copy lands at a new path, so shelves are seeded **after** the workspace and profile are allocated, written to that workspace's resolved production shelf path via the real `ShelfService`, with a test asserting they actually render in the UI (Codex #7).
    - **Both Memento stores** — `context.globalState` and `context.workspaceState`, used for selected repository, undocked selection, commit-checks cache, and the review-prompt latch.
    - **`context.secrets` (SecretStorage)** — `CredentialStore` wraps it at [repositoryMode.ts:214](src/activation/repositoryMode.ts:214), and the contributed `commitChecks.signIn`/`signOut` commands mutate it. Any flow covering those commands must assert secret state, using test-only credentials.
    - **VS Code configuration in every scope** (Codex R3 #3) — not only workspace settings. [repositoryMode.ts:1154](src/activation/repositoryMode.ts:1154) calls `config.update("undockableWindow", true, true)`, whose third argument writes **global** user settings that outlive any workspace.
    - **Per-webview persisted state** — `setState` is used at 10+ sites (`CommitPanelApp`, `UndockedApp`, `CommitGraphPanel`, `BranchColumn`, `useCheckedFiles`, …) and VS Code retains it for the webview's lifetime, so checked-file sets and group-by-dir toggles survive across a flow unless reset.

    Layer 2 launches with a disposable `--user-data-dir` / `--extensions-dir` per test, so these reset together.

    **The E2E control channel — without it, half of step 24 is unimplementable (Codex R4 #5).** Memento, SecretStorage, and per-webview `setState` live *inside the extension host*. Playwright drives VS Code from an **external process** and has no access to any of them: Mementos are internal VS Code storage, and SecretStorage is the OS keyring, which is not portably readable from outside. As written, the plan demanded exact assertions over stores nothing could read — a step that cannot be implemented, and if stubbed out, a silent false-green. So the extension exposes a **development-only control channel**. Its transport is **not** a command-palette command (Codex R5 #7): palette visibility requires a static `contributes.commands` entry, which would ship the control surface in the marketplace manifest — the exact thing the gating exists to prevent — and a palette invocation carries no structured arguments and returns no value, so it could not express a request or return a snapshot at all.
    - **Transport: a nonce-bound file exchange inside the fixture-owned root.** When active, the extension watches `$INTELLIGIT_E2E_CHANNEL_DIR` (allocated per test alongside `HOME`/`TMPDIR`). Playwright writes `<nonce>.request.json`; the extension writes `<nonce>.response.json` by temp-file-plus-rename so a reader never sees a partial write. Nothing is contributed to `package.json`, so there is nothing to strip at package time — and a packaging test asserts the produced `.vsix` manifest contains no control command.
    - **Three independent gates, all required:** `ExtensionMode.Development`, `INTELLIGIT_E2E=1`, and a channel directory that exists and is writable. A unit test asserts the watcher does not start under `ExtensionMode.Production` even with the variable set and the directory present.
    - **Allowlisted keys only** — an explicit list of the Memento keys, secret keys, and webview state keys this suite touches. An unlisted key is a rejection, not a passthrough.
    - **Secrets are reported as presence + digest, never as values.** The flows need "is `commitChecks` signed in", not the token; returning values would build a credential-exfiltration surface to satisfy a test assertion.
    - **Webview state needs a round trip, not a host read (Codex R5 #5).** `getState`/`setState` are the *renderer-side* API ([vscodeApi.ts:9](src/webviews/react/shared/vscodeApi.ts:9)); no extension-host API reads them, so a host-only channel could not implement this leg and would have returned empty results that read as "no state" — a false green. The channel therefore posts a **correlated** E2E message to the target webview and awaits its reply:
        - Handled in the single acquisition wrapper [vscodeApi.ts:29](src/webviews/react/shared/vscodeApi.ts:29), gated at runtime on a `window.intelligitE2E` flag that the shell injects **only** when the host gates above are satisfied. Runtime-gated, not build-gated, deliberately: a build-time `define` would produce a different bundle for tests than for production and destroy Layer 1's entire premise of pixel-testing the real artifact. The residual — handler code present in the shipped bundle — is bounded by the fact that webview messaging is reachable only from the extension host, behind the nonce CSP; an attacker able to post to it already controls the host.
        - **A missing, unmounted, or unacknowledged view is a hard failure**, never an empty snapshot. Each request carries a correlation ID and a timeout.
        - **Seeding updates both the persisted state and the mounted component**, since `setState` alone does not re-render React; the seed forces a remount and the oracle then verifies rehydration after a reload.
    - Operations: seed, snapshot, reset. Snapshot output feeds the step-24 durable-state oracle; seed makes the step-23 setup column reachable; reset backs the teardown assertions.

    **Fixture-owned scratch directories (Codex R3 #7).** The extension writes outside the repository, the profile, and every store above: `src/` contains **9** `mkdtemp(os.tmpdir(), "intelligit-*")` sites — [gitAskpass.ts:54](src/services/gitAskpass.ts:54), `shelfService` ×3, `shelfServiceCapture`, `shelfConflictSession` ×2, [operations.ts:984](src/git/operations.ts:984), and [patchApplication.ts:18](src/git/patchApplication.ts:18). An interrupted flow leaks these into the shared OS temp directory where no reset target reaches them, and a later test can observe them. Therefore each test allocates `HOME`, `TMPDIR`, `TMP`, and `TEMP` **beneath its own fixture-owned root**, and those directories are included in the canonical snapshot, in `dispose()`, and in the teardown assertions — including the throwing-teardown negative fixture.

### Phase 2 — Record real protocol payloads

11. `scripts/record-webview-fixtures.ts` runs the **real** git services against a seeded fixture workspace, captures the messages the extension posts to each webview — typed by [src/webviews/protocol/](src/webviews/protocol/) — and writes `tests/visual/fixtures/<webview>/<scenario>.json`.
12. **Determinism is not inherited from stable SHAs.** Real payloads carry random absolute workspace roots, UUID shelf/session IDs, and `Date.now()` values, any of which re-randomizes the JSON and therefore the screenshots. The recorder injects a fixed clock and a deterministic ID source, and canonicalizes environment paths to placeholders. A **record-twice byte-equality test** is the guard (Codex #10).
13. Recorded, not hand-written: a hand-written payload can stay type-valid long after the extension stopped emitting that shape, so you end up pixel-testing a screen no user ever sees. Re-running the recorder after a protocol change surfaces it as a reviewable JSON diff.

    **But "recorded once" decays into "hand-written" the moment an emitter changes (Codex R4 #2).** Record-twice equality (step 12) proves the *recorder* is deterministic; it never compares the recording against what is **committed**. A developer who changes a payload emitter and does not re-run the recorder leaves a stale-but-type-valid fixture on disk, the runtime validator accepts it, the screenshots match their equally stale baselines, and the whole pipeline is green while testing a screen the extension no longer emits — the exact failure this step exists to prevent, reintroduced through the back door. So **CI regenerates every canonical payload into a temporary directory and byte-compares it against the committed fixture**; any difference fails, with the diff printed. Updating a fixture becomes an explicit, reviewable commit, exactly like a baseline PNG.
14. Scenarios per webview: clean, dirty, conflicted, mid-rebase, detached HEAD, ahead/behind, empty repo, shelf-populated.

### Phase 3 — Layer 1: the visual harness

15. `tests/visual/harness/` renders a bundle inside a shell derived from **the production shell's own inputs**. The production shell [webviewHtml.ts:61](src/views/webviewHtml.ts:61) is not just two globals and a `#root`: it also emits a CSS reset, the `SYSTEM_FONT_STACK`, a 13px base size, a per-view `backgroundVar`, a `prefers-reduced-motion` block, `<html lang>` from the i18n payload, and per-view `styleFiles` links (the merge/conflict views have their own stylesheets). A harness missing any of these produces baselines for a layout production never renders (Codex #3). So:
    - A checked-in table encodes real shell options (`scriptFile`, `styleFiles`, `title`, `backgroundVar`) keyed by **production host context, not by bundle** (Codex R4 #4). Bundle→shell is **not 1:1**: `webview-mergeeditor.js` is hosted independently by [MergeEditorPanel.ts:343](src/views/MergeEditorPanel.ts:343) and [ShelfConflictEditorPanel.ts:141](src/views/ShelfConflictEditorPanel.ts:141), two separate `buildWebviewShellHtml` call sites that can drift apart in title, background, or stylesheet list. A 7-row bundle-keyed table can only encode one of them, so a regression in the other renders against a shell the drift guard never checks. Keying by **call site** is also wrong, and for the same reason one level up (Codex R5 #1): `CommitGraphViewProvider` is a single class with one `buildWebviewShellHtml` call site but is **constructed twice** — [repositoryMode.ts:283](src/activation/repositoryMode.ts:283) takes the default `webview-commitgraph.js`, [repositoryMode.ts:289](src/activation/repositoryMode.ts:289) passes `scriptFile: "webview-compactcommitgraph.js"` — so one call site resolves two different runtime hosts. **7 bundles, 7 call sites, 8 resolved host contexts.** The key is therefore the **resolved host context**, enumerated explicitly:

    | Context ID | Host | Bundle |
    |---|---|---|
    | `commit-graph-card` | `CommitGraphViewProvider` (default) | `webview-commitgraph.js` |
    | `commit-graph-compact` | `CommitGraphViewProvider` (sidebar) | `webview-compactcommitgraph.js` |
    | `commit-panel` | `CommitPanelViewProvider` | `webview-commitpanel.js` |
    | `commit-info` | `CommitInfoViewProvider` | `webview-commitinfo.js` |
    | `undocked` | `UndockedViewProvider` | `webview-undocked.js` |
    | `merge-editor` | `MergeEditorPanel` | `webview-mergeeditor.js` |
    | `shelf-conflict-editor` | `ShelfConflictEditorPanel` | `webview-mergeeditor.js` |
    | `merge-conflict-session` | `MergeConflictSessionPanel` | `webview-mergeconflictsession.js` |

    Where two rows share a bundle (`merge-editor` / `shelf-conflict-editor`), the guard additionally asserts they remain equivalent modulo explicitly listed fields, so an *intentional* divergence has to be declared.
    - The harness composes the shell from that table plus the Phase 0 host fixture (root CSS vars + `html`/`body` classes + datasets).
    - `window.acquireVsCodeApi` is stubbed at the single acquisition point [vscodeApi.ts:29](src/webviews/react/shared/vscodeApi.ts:29), recording outbound `postMessage` calls for assertion.
16. **Drift guard (Phase 6):** normalize and compare the production HTML from `buildWebviewShellHtml` against the harness HTML for **every host context in the step-15 table** — bootstrap globals, root element, `lang`, inline style block, background, and the full stylesheet/asset list. Not just the globals, and not one row per bundle. A completeness assertion pins the table to reality — but it must be **exact set equality over context IDs, not a count** (Codex R5 #1). Every `buildWebviewShellHtml` invocation is tagged with its context ID; a probing run collects the IDs actually produced, and the test asserts that set equals the table's key set exactly. A count check would pass while one context was missing and another duplicated, which is precisely the shape of the defect being fixed.
17. `scripts/webview-harness-server.js` generalizes the existing [preview-merge-editor.js](scripts/preview-merge-editor.js) static server to serve any `WEBVIEW_CONFIGS` bundle with a chosen fixture, host fixture, and theme, selected by query param. Wired as Playwright's `webServer`, after the Phase 0 build gate.
18. `playwright.visual.config.ts`: Chromium only, `--disable-gpu` (software rasterization, for canvas stability), `reducedMotion: 'reduce'` (framer-motion is a dependency), `deviceScaleFactor: 1`, fixed `timezoneId` and `locale`. Matrix: **dark + light × 2 viewports** — narrow (≈320px, sidebar) and wide (≈1200px, undocked), where the layout genuinely branches, as [sectionWidths.ts](src/webviews/react/undocked/sectionWidths.ts) shows. (An earlier draft cited `undocked-section-widths.test.ts` for this; that citation was **wrong** and is withdrawn — the test only exercises a 1200px layout and demonstrates no narrow/wide branch at all, Codex R5 #8.) 4 baselines per screen. `threshold: 0.2`, `maxDiffPixels: 0`.
19. **Non-pixel coverage for the axes left out of the matrix.** High-contrast (using the Phase 0 `hc-black`/`hc-light` host fixtures) and all 12 locales get computed-style assertions instead of PNGs. The naive overflow check is wrong in **both** directions and is not used (Codex R2 #4): `scrollWidth <= clientWidth` cannot see *vertical* clipping, and it false-**reds** on every one of the 5 intentional `text-overflow: ellipsis` declarations already in the webview CSS. Instead:
    - Elements opt in by declaration. A **non-truncatable** element (one whose full text must be visible) is checked in **both** dimensions, and **against every clipping ancestor plus the viewport** — an element whose own `scrollWidth`/`scrollHeight` fit can still be clipped by an ancestor with `overflow: hidden` or by the viewport edge, which the self-relative check reports as green (Codex R3 #2). The oracle therefore intersects the rendered text range's bounding rects with each clipping ancestor's content box and with the viewport, and fails on any loss. A parent-clipping known-bad fixture is registered.
    - A **truncatable** element (intentional ellipsis) is exempt from the overflow check and instead asserts its **computed accessible name** (or accessibility-tree text) equals the untruncated source string. Requiring a `title` or `aria-label` specifically would be wrong (Codex R3 #8): an accessible name can legitimately come from DOM content, `aria-labelledby`, or a native `<label>`, so an attribute-presence check produces false failures while missing the case where the name is present but *itself* truncated. Truncation that loses the content entirely is the real defect, and the computed-name comparison is what catches it.
    - Plus: no zero-size interactive targets, no transparent-on-transparent pairs, and a foreground/background contrast-ratio floor.

    A German string overflowing a non-truncatable label still fails CI without 12× the baselines.
20. **Baselines are container-generated only**, committed under `tests/visual/__screenshots__/`. The image is pinned **by digest, not by the mutable `v<X>-jammy` tag** (Codex #13), and both `test:visual:update` *and* the CI comparison assert matching image digest, browser version, OS, and a font manifest — an update produced anywhere else is rejected. CI never self-heals; re-approval is a human reading the PNG diff GitHub renders inline in the PR.

### Phase 4 — Layer 2: ~10 critical flows on every PR

21. `playwright.e2e.config.ts` + `tests/e2e/`, with a `fixtureWorkspace` Playwright fixture wrapping Phase 1 and a per-test disposable profile.
22. Thin page objects: `Workbench` (command palette, notifications, quick pick), `IntelliGitView` (webview frame resolution), plus per-screen objects.
23. **Every flow is specified as a row in a checked-in matrix**, not as a bare command name: `setup → action → UI oracle → local-git oracle → origin oracle → durable-state oracle`. The setup column is load-bearing: force-push-with-lease against no stale lease, or abort against no live operation, exercises a guard and passes without ever reaching the feature (Codex #15). Setups include a collaborator-created remote commit, rewritten history, a stale lease, and an in-flight operation.
24. Oracles are **four-way**, not three-way (Codex #6): the UI state, the local repository (asserted by shelling `git` directly, not through the extension), **the bare `origin`** (or a fresh clone of it, for push/force-push/publish), and **durable extension state** (shelf store, rebase manifest, and exact absence of `repo.lock` / `takeover-*` residue). The shelf store and manifests are plain files the test process reads directly; Memento, SecretStorage, and webview `setState` are reachable **only** through the step-10 E2E control channel, which is therefore a hard prerequisite of this step rather than an implementation detail.
25. The ~10 highest-blast-radius flows: commit, push, pull, interactive rebase, merge-conflict resolve, shelf apply, branch checkout, force-push-with-lease, discard changes, abort active operation.
26. VS Code version pinned to a constant, not `stable`, so a VS Code release cannot turn CI red overnight.
27. CI: a new job on the existing workflow under `xvfb-run -a`, uploading Playwright traces and failure screenshots. Target: PR feedback under ~5 minutes with Layers 1 and 2 in parallel jobs.

### Phase 5 — Nightly full sweep

28. **The mutating surface is defined by a checked-in manifest, not by a number in this document.** The earlier "42 mutating commands" was derived by regex over `contributes.commands` and is wrong: of 69 contributed commands, **8 are `.color` icon aliases** of existing commands (61 unique bases), and the count also missed mutating actions reachable only from inside a webview (commit, stage, discard), which are not contributed commands at all. A `tests/e2e/coverage-manifest.ts` maps every mutating command **and webview action** → scenario or an explicit `not-covered: <reason>`, with alias collapsing, and a test asserts the manifest is exhaustive against both `package.json` contributions and the registered handlers (Codex #16).
29. A scheduled workflow runs the full manifest sharded 4 ways.
30. **Insiders early-warning applies to Layer 2**, which actually launches VS Code. Running Layer 1 "against Insiders" would change no tested input — it is plain Chromium reading committed fixtures (Codex #17). Layer 1 gets Insiders coverage only via **freshly captured Insiders host fixtures**, compared against the pinned ones; a diff in the captured tokens/classes is the early warning.
31. **The release gate is made real — and the nightly is not it.** Today `release: needs: build` and the tag is created on a main push, so a separate scheduled job cannot block it (Codex #18); the earlier claim that "nightly red blocks the release tag" was simply false. The v2 fix — gate the release on a same-SHA nightly attestation — was *also* broken: a version-changing push runs `release` before any nightly for that SHA exists, and a later nightly success never retriggers it, so there was no automatic attested release path at all (Codex R2 #8). The correct shape separates the two jobs by purpose:
    - **Nightly = early warning only.** Scheduled, sharded, not on the release path. Its failure opens an issue; it gates nothing.
    - **Release gate = a same-SHA full sweep the release job depends on.** `e2e-full` runs the full coverage manifest for the commit being tagged, so the gate always exists when the release runs — no ordering hole, no retrigger requirement.
    - **`needs:` alone does not implement the override (Codex R3 #9).** A failed `needs:` dependency makes GitHub *skip* `release` outright, so the promised recovery lever would not exist; the current `force_publish` input bypasses only the version comparison, not a gate. So `release` declares `needs: [build, e2e-full]` **with an explicit `if:`** that always requires `build` to have succeeded and requires `e2e-full` to have succeeded *unless* a separate, audited `skip_e2e_gate` dispatch input is set — evaluated with `always()` so the job is reachable when the gate fails.
    - **`e2e-full` must be guarded off pull requests (Codex R3 #10).** This workflow also triggers on `pull_request`, and its existing jobs already use explicit `if:` guards for exactly this reason. An unguarded `e2e-full` would run the entire sweep on every PR and silently destroy the settled ~10-flow PR tier. It is therefore restricted to main-branch pushes and manual dispatches; the critical-flow job remains the PR-tier dependency.

### Phase 6 — Unit tests for the new infrastructure

Vitest suites, added to the existing coverage gate. **Every oracle below gets a known-bad fixture proving it goes red** (Codex #19) — otherwise inverted or no-op assertion code stays green forever.

32. **Seed determinism, over the canonical snapshot — not just git objects.** Equal SHAs, raw logs, and tree hashes say nothing about ignored/untracked bytes, index flags and unmerged stages, stash, reflogs, config, bare-origin state, or post-allocation shelf state (Codex R2 #7). So: seed and **fully initialize** two independent workspaces (copy allocated, profile allocated, shelves seeded), then compare their **normalized step-9 canonical snapshots** for equality. Run the same comparison under a *hostile* ambient environment — a global `.gitconfig` with a different user, a non-UTC `TZ`, `core.autocrlf=true` — to prove the sanitization in step 7 actually holds (Codex #8).
33. **Restore fidelity** — mutate a workspace, restore, and assert the result equals the **canonical initial snapshot** from step 9, item by item. Not merely "a fresh copy is unaffected", which stays green even when every copy starts wrong (Codex #2).
34. **Resource cleanup** — after `dispose()`, assert every allocated resource is gone: workspace copy, origin copy, profile dir, linked worktrees outside the root, and spawned processes. Asserted for both successful **and failing** teardown paths.
35. **Isolation** — mutate workspace A destructively (`git gc --prune=now`, force-push, `worktree add`); assert workspace B and the template are byte-identical to before.
36. **Protocol conformance that can actually fail** — `tsconfig.json` excludes `tests` and `tsconfig.webview.json` covers only `src/webviews/react/**`, and vitest transpiles without type-checking, so a type-only assertion on the recorded fixtures could never go red in CI (Codex #5). Fix: a `tsconfig.tests.json` added to the `typecheck` script, **plus** runtime validators that reject a malformed fixture at test time.

    **The negative fixture cannot live in that project (Codex R4 #7).** A deliberately type-invalid fixture inside `tsconfig.tests.json` makes the mandatory typecheck fail permanently; excluding it proves nothing about the project's wiring — the two obvious placements are a broken build and a no-op. So the expected-failure case compiles through a **separate `tsconfig.tests-negative.json` that extends `tsconfig.tests.json`** (inheriting the exact compiler options under test, so it cannot drift into laxness) over a fixture directory excluded from the main project, run as a subprocess that the test asserts exits **non-zero with the expected diagnostic code**. A green `tsc` there is the failure.

    **And the negative project alone proves nothing about the positive one (Codex R5 #4).** `tsconfig.tests-negative.json` fails correctly even if the production `typecheck` script never references `tsconfig.tests.json` at all — leaving the original blind spot exactly where it was, now with a passing test beside it. So the check runs in two parts: first execute the **real `typecheck` command** and assert it succeeded *and* that its project graph actually covered the recorded-fixture files (a deliberately type-invalid file temporarily placed in the positive project must turn that command red); only then run the expected-failure project.
37. **Recorder determinism** — record twice, assert byte-equal JSON (step 12).
38. **Harness shell drift guard** — step 16, all 7 bundles.
39. **Host fixture staleness — recapture and compare content, not just provenance (Codex R4 #3).** Checking only provenance certifies the *label*, not the artifact: a fixture whose CSS variables, class lists, or datasets are wrong but whose metadata is well-formed passes, then generates self-consistent baselines for a host VS Code never produces — the pixel diff agrees with itself forever. So the job **recaptures all four host fixtures in the pinned container** (same code path as step 4) and byte-compares the canonicalized capture against each committed artifact. Provenance mismatch remains a failure; content mismatch is now also a failure, and it is the one that catches a VS Code theme-token change.
40. **Oracle self-tests, driven by a registry that is structurally impossible to bypass.** A registry plus "assert every *registered* oracle has a fixture" is self-referential — omitting an oracle from the registry still passes, so the check certifies only what was already remembered (Codex R3 #1). The registry is therefore made the **only** path to invoking an oracle: every oracle is defined in `tests/oracles.ts` and consumed exclusively through `oracles.get(id)`, with a lint rule forbidding direct imports of oracle implementations. An unregistered oracle is then unusable rather than merely unaudited, and the meta-test asserting one expected-failure fixture per registered oracle becomes exhaustive by construction.

    Registered oracles and their known-bad cases:
    - Non-truncatable horizontal clipping → an over-long label; **vertical** clipping → a wrapped multi-line label in a fixed-height box.
    - Truncatable accessible-text (step 19) → **not** "an ellipsized element with no `title`/`aria-label`", which was a leftover from the rejected attribute-presence oracle and is not a failing case at all (Codex R4 #6): such an element still derives its accessible name from its full DOM text, so step 19 correctly passes and the fixture proves nothing. The real known-bad cases are elements whose *computed name* diverges from the source string — an `aria-label` overriding the text with a shorter or different value, an `aria-hidden`/empty-name element, and text truncated in the DOM itself rather than by CSS.
    - Zero-size interactive target → a `0×0` button. Overlap → two stacked controls.
    - Contrast floor → a low-contrast pair, **including the opaque-over-opaque case**, not only transparent-on-transparent.
    - Host-fixture replay → a dark bundle rendered against the light host fixture, and against a fixture with the correct CSS vars but the *wrong* body class.
    - Harness-server routing → an invalid route, and a route serving the wrong bundle for the requested webview.
    - Four-way flow oracles (step 24) → **five** fixtures, each corrupting exactly one leg: **UI-wrong-but-git-correct**, UI-correct-but-local-git-wrong, local-correct-but-**origin**-wrong, git-correct-but-**durable-state**-wrong, and everything-correct-but-**lock residue** present.
    - Pixel comparator (step 18) → a baseline deliberately altered by more than `maxDiffPixels`, proving the comparison is wired and not silently skipped for a missing baseline.
    - Seed/recorder determinism (steps 32, 37) → an intentionally nondeterministic seed and an unpinned-clock recorder, both of which must be caught.
    - Shell drift guard (step 38) → a harness shell missing a production stylesheet link; plus a host-context table with one context missing and another duplicated, which must fail the set-equality check a count check would pass (step 16).
    - Host-fixture staleness (step 39) → **two** fixtures, because the interesting one is not the obvious one (Codex R5 #3): a fixture with mismatched provenance, **and** a fixture with entirely *valid* provenance whose CSS variables and body classes have been corrupted. The second is the case the recapture-and-compare check exists for; testing only the first would leave the original provenance-only behaviour in place with a green test beside it.
    - **Build provenance (step 2)** → a `dist/` carrying a stale bundle whose content hash does not match the build record (must fail the gate), and a webview entry whose esbuild invocation throws (must fail the **build**, not be reported as "skipped, not found").
    - **Committed-payload freshness (step 13)** → a committed fixture altered by a single byte relative to what the recorder regenerates, which the CI byte-comparison must reject.
    - Baseline hygiene (step 41) → an orphan PNG with no owning test, and a matrix entry missing one of its 4 baselines.
    - Symlink containment and inode separation (step 8) → a copy containing an escaping symlink, and a deliberately hardlinked regular file.
    - Scratch-directory ownership (step 10) → a flow that leaks an `intelligit-*` directory into the process-wide OS temp dir instead of the fixture-owned root.
    - Restore fidelity (step 33) → a workspace restored from a deliberately incomplete snapshot.
    - Resource cleanup (step 34) → a `dispose()` that leaks a linked worktree, and one that throws mid-teardown.
    - Isolation (step 35) → a deliberately hardlinked copy, which must be detected.
    - Protocol conformance (step 36) → a fixture that is structurally invalid (must fail the runtime validator) **and** one that is type-invalid (must make the `tsconfig.tests-negative.json` subprocess exit non-zero with the expected diagnostic), proving both halves are wired without breaking the mandatory typecheck.
    - **E2E control channel (step 10) → the complete negative matrix, not two samples** (Codex R5 #2). A channel that silently no-ops makes every step-23 setup column vacuous while the whole suite stays green, so each way it can lie gets its own fixture:
        - **Gating truth table, all four cells**: {`Development`, `Production`} × {`INTELLIGIT_E2E=1`, unset}. Exactly one cell may activate the watcher; the other three must not, including `Production` with the variable set and the channel directory present.
        - **Table-driven seed → snapshot → reset**, per allowlisted key: a seed that no-ops must be caught by the following snapshot, and a reset that no-ops must be caught by the snapshot after it. A constant-returning snapshot fails every row.
        - **Allowlist rejection** — an unlisted Memento, secret, or webview-state key must be rejected, not passed through.
        - **Secret redaction contract** — a channel returning a raw secret value instead of presence + digest must fail.
        - **Webview leg** — a request to an unmounted or unacknowledged view must fail loudly rather than return an empty snapshot; a seed that writes persisted state without remounting must be caught by the post-reload rehydration assertion.
        - **Packaging** — the produced `.vsix` manifest must contain no control command.
41. **Baseline hygiene** — every committed PNG maps to a live test name (no orphans), and every test in the matrix has all 4 baselines (no silent gaps).

## Key decisions & tradeoffs

| Decision | Chosen | Rejected, and why |
|---|---|---|
| Framework | **Playwright** | Cypress cannot drive Electron/VS Code at all. Not a close call. |
| Scope | **Both layers, staged** | Layer 1 alone leaves "dedicated repo for all the actions" unmet; Layer 2 alone is slow, flaky, and pixel-noisy through VS Code chrome. |
| Fixture repo | **Seed script → template → contract-checked recursive copy per test** (equivalent to the template modulo declared live path rewrites) | `git clone` silently drops untracked/ignored/index/config/stash/sequencer state — the exact state these tests act on. A checked-in `.bundle` is an unreviewable binary; a real GitHub repo adds network, auth, and shared mutable state to CI. |
| Reset strategy | **Discard the copy, re-copy from template** | In-place undo is where partial-restore bugs live. |
| Layer 2 driver | **Playwright `_electron` on a pinned `@vscode/test-electron` binary** | `wdio-vscode-service` adds a *third* runner with its own config, reporter, CI job, and flake surface. The in-host Mocha runner is least flaky but cannot click or screenshot. |
| E2E gate | **~10 flows on PR, full manifest nightly** | All flows on PR ≈ 15–30 min even sharded, and enough real-VS-Code surface that intermittent flake trains the team to ignore red CI. |
| Baselines | **Committed PNGs, digest-pinned container, explicit opt-in update** | Artifact-cached baselines hide the baseline from PR review; no-pixel-baselines defeats the purpose. |
| Matrix | **dark + light × 2 viewports (4/screen)** | Adding high-contrast is +50% PNGs on every intentional change; a locale sweep is 12×. Both get non-pixel coverage using the captured HC host fixtures. |
| Payloads | **Recorded from the real fixture repo, with injected clock/IDs** | Hand-written payloads drift silently into states the extension no longer emits. |
| Unit tests | **The new infrastructure, each oracle proven to fail** | A React component backfill would duplicate Layer 1 in a layout-engine-free medium. |

Two consequences worth naming: **committed PNGs grow the repository** (capped by 4 baselines per screen; the repo already carries 14 MB `.vsix` files), and **a developer cannot regenerate a baseline without Docker** — deliberate, since the alternative is macOS baselines that fail every CI run.

## Risks / open questions

- **R1 — `_electron` reaching nested webview iframes.** Phase 0 exists to prove this before anything is built on it.
- **R2 — Font rendering inside the container.** `SYSTEM_FONT_STACK` resolves per installed fonts. Mitigated by pinning the image **by digest** and asserting a font manifest on both update and compare (step 20).
- **R3 — Canvas rendering.** The commit graph paints to a canvas ([useCommitGraphCanvas.ts](src/webviews/react/commit-list/useCommitGraphCanvas.ts)); GPU vs software rasterization is the classic 1-pixel flake source. Mitigated by forcing software rasterization. **If a mask is ever needed, it may not be applied bare** — a mask deletes real coverage of paint, colour, scaling and compositing, so any masked region must ship with a replacement oracle in the same change. Building that oracle *now*, before flake is observed, is speculative work and is deliberately deferred.
- **R4 — Linked worktrees escape the workspace root.** `worktree add` writes outside it; `dispose()` enumerates and removes them (step 9).
- **R5 — Test wall-clock.** If Layer 2's 10 flows exceed ~5 minutes on PR, the tier boundary moves rather than the flakiness being tolerated.
- **R6 — Directory copy cost.** Copying the template per test is slower than a hardlinked clone. If the template grows enough for this to dominate, the mitigation is a smaller template, **not** a return to cloning, and **not** hardlinking — step 8 asserts no regular file shares an inode with the template, precisely because a hardlinked copy lets one test's mutation corrupt every other.
- **R7 — Copy-contract drift.** The copy is a *contract-checked recursive copy modulo declared live rewrites* (step 8) — never byte-identical, since rehydration deliberately writes concrete per-test absolute paths. If a future fixture adds state containing absolute paths that nobody adds to that set, copies diverge silently. Mitigated by the post-copy diff assertion: anything differing from the template that is not a declared rewrite fails.
- **Resolved (was open):** the coverage manifest (step 28) **hard-fails on an unmapped mutating command or webview action from its first enforced run.** A warn-for-one-release grace period would contradict the exhaustiveness assertion in the same step and would let an unmapped mutating handler land with green CI (Codex R2 #2) — which is the precise failure this manifest exists to prevent. The map is filled in before the check is turned on, not after.

## Out of scope

- Backfilling jsdom unit tests for the 84 untested React components.
- Visual testing of native VS Code UI outside IntelliGit's own webviews.
- Cross-browser visual testing — the webview host is always Chromium.
- Windows and macOS E2E runners; Linux only for now.
- Performance/load testing, and testing against real remote hosts (GitHub, Bitbucket) — the fixture `origin` is always local.
- Replacing or restructuring the existing 168-file vitest suite.
