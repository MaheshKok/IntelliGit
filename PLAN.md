# Plan: Interactively Rebase From Here (PyCharm parity)

_Locked via grill — by Claude + maheshkokare. Revised after Codex Rounds 1–7 (50/50 findings addressed)._

## Goal

Replace the current terminal-based `interactiveRebaseFromHere` with a PyCharm-parity "Rebasing Commits" dialog: right-click a commit in any of the three commit-list surfaces → a modal overlay lists the range (selected → HEAD) with per-commit actions (pick / reword / squash / fixup / drop), inline message editing, and reordering (drag + up/down). "Start Rebasing" runs `git rebase -i` headlessly by injecting the generated todo via `GIT_SEQUENCE_EDITOR` and supplying reword/squash messages via `GIT_EDITOR` — no terminal, no user-facing todo file. Conflicts pause into the existing conflict UX with in-product Continue/Abort; rebases that rewrote pushed commits end with a one-click force-push (with lease) offer.

## Approach

1. **Executor env support** — `GitBinaryRunOptions` gains `env?: Record<string, string>`; `spawn` merges it over `process.env`. Expose through a `run`-level options path so `rebase` calls can pass env. Unit-tested.
2. **Rebase domain module** (`src/git/interactiveRebase.ts`, pure + small service):
   - Types: `RebaseAction = "pick" | "reword" | "squash" | "fixup" | "drop"`, `RebaseTodoEntry { hash, action, message? }`.
   - `buildRebaseTodo(entries)` → todo content in dialog order (oldest first), explicit `drop` lines.
   - **Strict submission validation (fail closed):** action must be one of the five allowed values (exact allow-list, nothing else reaches a todo line); every hash must be a full 40/64-char hex string AND a member of the host-recorded offered range set; no duplicates; entry count must equal range count; reject any CR/LF/NUL or non-hex characters in hashes and actions. **Messages may contain CR/LF and reject only NUL** (amended after Phase 4a — see below); messages required non-empty for reword/squash.

   > **Amendment (Phase 4a, user-authorized).** As originally frozen, step 2 rejected CR/LF in `entry.message` while step 6 specified an inline editor that "expands" for reword/squash and "pre-fills combined messages". Those are contradictory: the validator rejected 100% of squashes and every reword of a commit with a body. Seven review rounds missed it. Resolved in favour of step 6 and PyCharm parity — a reword must be able to carry a commit body. The todo file stays safe without the validator's help: `buildRebaseTodo` independently truncates each entry to its first physical line and strips CR/LF/NUL, so a multi-line message can never inject a todo line. Consequence for step 7: the keyed message map must carry the **full** multi-line message to `GIT_EDITOR`, not the todo-line subject. First **non-dropped** entry cannot be squash/fixup (validator rule; UI mirrors it — see step 6).
   - **Atomic reservation before enqueue (TOCTOU fix):** a per-repo reservation is taken with an atomic filesystem primitive (`O_EXCL` pointer file under extension storage) BEFORE the rebase command is queued; a submission that cannot take the reservation (or finds `rebase-merge`/`rebase-apply` present) is rejected. The start sequence then runs **inside the repository mutation gate** as one critical section: re-verify `HEAD == expectedHead` and all guards immediately before spawning `git rebase` (via `RepositoryMutationGate.run` around an ungated `runBinary`, so check+spawn are not separated by queued mutations). Git's own rebase lock is the backstop, never the guard.
   - **Per-submission unique session directory** holding helper artifacts only: todo content, the keyed message map, consumption markers. The versioned **session manifest** lives OUTSIDE the session directory in a per-repo manifest store under extension storage (it must outlive helper-artifact cleanup — see steps 7–8): `{ version, sessionId (uuid, shared with the reservation, the session-dir name, and the in-rebase-dir marker), repoRoot, branch (fully qualified, from `symbolic-ref -q HEAD` — the same form as `rebase-merge/head-name`, so correlation compares like with like; the short display name is derived separately), pushTarget? ({ remoteName, remoteHeadRef (fully qualified), upstreamOid } — **all-or-none optional**: created only when the branch's configured upstream is a **non-local remote** (`branch.<name>.remote` ≠ `.`) with a resolvable remote-tracking ref at submission, the remote resolves to **exactly one effective push URL**, and that URL does **not canonicalize to the current repository** — a local upstream, a named self-remote, or a multi-push-URL remote never arms the offer (with multiple push URLs one endpoint can be force-updated before another rejects the lease, leaving partial remote state); absent otherwise, which disables the offer; manifest validation covers both forms), baseHash, expectedHead, createdAt, lifecycle: "starting" | "running" | "paused" | "completed-pending-push" | "done", rebasedHeadOid? (set on success) }`. **Every manifest write goes through a validated temp file + atomic rename**; recovery treats truncated, corrupt, or unknown-version manifests as ambiguous (surface notice + discard action), never as actionable state.
   - **Reservation lifecycle (no leaks):** every exit path that is not verifiably paused/running — in-gate recheck failure, spawn error, immediate rebase failure with no `rebase-merge`/`rebase-apply` left behind — releases the reservation and deletes the session directory. Activation additionally runs an **orphan sweep**: a reservation pointer with no rebase dir and no live manifest is reclaimed.
3. **Editor helper script** — a standalone `.cjs` built as a second esbuild entry.
   - **Invocation contract:** git runs editors via its sh. The editor command is built with a single specified POSIX/MSYS-safe quoting algorithm — single-quote wrapping with the `'\''` escape rule, backslashes normalized to forward slashes first — applied to `process.execPath` and the script path, and **prefixed with `env ELECTRON_RUN_AS_NODE=1`** so the variable is scoped to the editor invocation only (it is NOT placed in the parent `git rebase` environment, where hooks and their children would inherit it). The full command string is round-tripped through a real child sh in tests using every metacharacter class: spaces, backslashes, apostrophes, double quotes, `$`, backticks, newlines, non-ASCII.
   - `sequence` role: overwrite the todo file with session todo content, then write a `sessionId` **marker file** into the rebase state directory (`rebase-merge/intelligit-session`). Git's rebase machinery reads only its known filenames and removes the directory wholesale on finish/abort, so the marker cannot leak. The marker is what makes a rebase dir *ours* — read-only metadata correlation alone cannot distinguish an identical-input restart (see step 8).
   - `message` role — **keyed with consumption tracking, fail closed:** the session stores `{ originalHash → { action, message } }` plus a consumed set. The script resolves the current step from the tail of `rebase-merge/done` (action + hash matching the todo we generated; `msgnum` as fallback). Exactly three outcomes: (a) step resolved and key present → write the message, mark consumed; (b) step positively identified as one that carries no prepared message (e.g. a post-conflict prompt for a `pick`) → leave the file untouched, exit 0; (c) step cannot be resolved while unconsumed prepared messages remain → **exit nonzero** so git stops the rebase at that step — the session is preserved, the failure is surfaced with Continue/Abort, and a submitted reword/squash edit is never silently discarded. Before any keyed lookup the script revalidates the `sessionId` marker against its session; marker absent or mismatched → outcome (c) — it never injects into a rebase that is not ours.
4. **Extension command rewrite** (`commitHistoryActions.interactiveRebaseFromHere`):
   - Guards: on a branch (no detached HEAD), selected commit non-merge, ancestor of HEAD, has a parent, clean working tree, no merge commits anywhere in `<hash>^..HEAD`, no whole-index operation in progress, reservation available.
   - **Drop the unpushed-only guard** (grill decision): pushed commits allowed; compute per-commit pushedness for the dialog warning.
   - **Range size bound:** the range is capped (constant, 500 commits) — larger ranges are rejected with a clear error before any dialog opens. Range loading uses `runBinary` with `maxOutputBytes` and treats truncation as a hard error, so a pathological body cannot exhaust the extension host.
   - Gather range with a **NUL-only, fixed-arity format**: `git log --reverse -z --format=%H%x00%an%x00%aI%x00%B` — `-z` makes git NUL-terminate every record, replacing the newline it otherwise inserts between entries (verified against real git: without `-z`, records arrive as `...%B\0\n<next hash>`, corrupting every multi-commit parse), and the format carries no trailing `%x00` of its own (which would double-terminate). The output is one NUL-separated stream: split on NUL, verify and discard exactly one trailing empty sentinel, then group by arity of 4. Git forbids NUL in every one of these fields (including `%B`), so no in-band collision exists; bodies containing SOH/control bytes are covered by tests. Malformed arity → reject.
   - Register a **host-side pending dialog request**: `{ requestId (crypto.randomUUID, single-use), originProvider (provider-instance identity), repoRoot, baseHash, rangeHashes, expectedHead, expectedBranch (fully qualified symbolic ref) }` kept in extension memory, then post `showRebaseDialog { requestId, commits, branch, hasPushed }` to the **originating provider only**. `expectedBranch` closes the same-tip hole: two branches can share one OID, so HEAD equality alone cannot prove the checked-out branch is still the one the dialog was opened on.
5. **Protocol + one-shot submission** — new messages in `commitGraphTypes.ts` (and panel/undocked unions as needed): host→webview `showRebaseDialog`; webview→host `startInteractiveRebase { requestId, entries }` / `cancelRebaseDialog { requestId }`. The webview never sends a base hash. On submit the host consumes the pending request by `requestId` **only when the inbound message arrives from the recorded origin provider**; requests expire on cancel, provider disposal, repo switch, or timeout. It then re-checks `HEAD == expectedHead` **and current branch == expectedBranch (exact ref equality)**, repo unchanged, guards, and entry validation (step 2) — with the final HEAD+branch/guard re-check repeated inside the mutation-gate critical section (step 2), covered by a same-tip branch-switch regression test. Stale, unknown, or wrong-origin `requestId` → clear error, no rebase.
6. **RebaseDialog webview component** (`src/webviews/react/shared/components/RebaseDialog/`), mounted by the three commit-list hosts — **`CommitGraphApp` (editor graph panel), `CompactCommitGraphApp` (the `sidebarGraph` `CommitGraphViewProvider` view), `UndockedApp`** — following the ShelveDialog overlay pattern; the dialog-open message is routed only to the provider that dispatched the menu action:
   - Rows oldest-at-top (todo order): action selector, subject (inline editor expands for reword/squash — squash pre-fills combined messages), short hash, author, date. Row list virtualized or bounded by the 500-commit cap.
   - Reorder via up/down buttons and drag-and-drop. The **first-non-dropped rule is recomputed after every action change and reorder**: squash/fixup are disabled (and cleared with a visible notice if they become invalid) on whichever row is currently the first non-dropped one — UI and validator enforce the same predicate.
   - Pushed-history warning banner when the range includes pushed commits; Start Rebasing / Cancel; focus management per existing dialog conventions.
7. **Run the rebase** — under `runWithNotificationProgress`: write session files + manifest (lifecycle `starting`) → in-gate recheck → `rebase -i <base>` with `GIT_SEQUENCE_EDITOR`/`GIT_EDITOR` env (helper commands carry their own `env ELECTRON_RUN_AS_NODE=1` prefix) → on success: record `rebasedHeadOid`, delete helper artifacts + release the reservation, then: push offer due → lifecycle `completed-pending-push`, **manifest retained** until push success or explicit discard (then marked `done` and removed); no push offer → lifecycle `done`, **manifest deleted immediately** — a directly-`done` session must never resurface as an ambiguous moved-HEAD manifest on the next activation. Success toast, `refreshAll`.
   - **Pause classification (conflict vs helper stop)**: on non-zero exit with `rebase-merge`/`rebase-apply` present, inspect the index for unmerged entries (`git ls-files -u`). Unmerged entries → conflict pause: lifecycle `paused`, notification "Rebase paused on conflict — resolve, then Continue"; existing conflict UI handles resolution. No unmerged entries → editor/helper stop (deterministic failure, e.g. the fail-closed script exit): surface the captured stderr with guidance — Continue retries the step, Abort backs out — and do NOT tell the user to resolve files that aren't conflicted. Session + manifest persist in both cases.
   - **Force-push offer (source- and destination-pinned)**: offered only when the range included pushed commits and the manifest carries a `pushTarget` (an upstream existed at submission). On click: re-verify the current branch equals the manifest branch AND current `HEAD == rebasedHeadOid` (else abort with "branch moved since the rebase — push manually"); then push the exact object: `git push <remoteName> <rebasedHeadOid>:<remoteHeadRef> --force-with-lease=<remoteHeadRef>:<upstreamOid>`. The lease pins the destination to its pre-rebase state; the explicit source OID pins what is pushed — later local commits or resets can neither widen the lease nor be force-pushed accidentally. The toast carries an explicit **Dismiss** action alongside Force Push: Dismiss marks the session `done` and deletes the manifest (the user pushes manually later) — a dismissed live offer never leaves a dangling `completed-pending-push` manifest for reload reconciliation to trip on.
8. **Continue/Abort affordance** — the host snapshot/protocol gains a **discriminated operation kind** (`activeOperation: "none" | "merge" | "cherry-pick" | "revert" | "rebase"`, derived from the ref/dir set the whole-index watcher already tracks) plus, when the kind is `rebase`, a **rebase-control discriminator** (`rebaseControl: "owned" | "unowned" | "foreign"` — owned: marker matches the live manifest → full Continue/Abort with message injection; unowned: rebase dir without any manifest → Continue/Abort without injection; foreign: marker absent/mismatched while our manifest exists → Abort-only) so the Toolbar can actually render the three reconciliation outcomes the matrix below promises; all three states protocol- and toolbar-tested instead of overloading the whole-index boolean and unmerged-file heuristics: the commit-panel Toolbar shows "Continue Rebase" / "Abort Rebase" when the kind is `rebase` (and **suppresses the Abort Merge button** — no duplicate abort controls during a conflicted rebase). The existing Abort Merge affordance is otherwise **unchanged in visibility**: it still appears on unmerged files (`hasMergeConflicts`, CommitTab.tsx) for `merge`/`cherry-pick`/`revert` states — narrowing it to `kind === "merge"` would silently remove today's only abort control for conflicted cherry-picks and reverts. One **pre-existing dispatch gap is fixed alongside**: `GitOperations.abortMerge` (operations.ts:1642) handles MERGE_HEAD/REBASE_HEAD/CHERRY_PICK_HEAD but has no `REVERT_HEAD` branch, so a conflicted revert falls through to generic `reset --merge`, which strands `.git/sequencer` on multi-commit reverts. It gains a `REVERT_HEAD → git revert --abort` dispatch before the generic fallback. A conflict-free rebase pause (helper stop, reword step) is therefore still identifiable and actionable. Continue/Abort side effects are **scoped by `rebaseControl`**: `owned` → Continue runs `rebase --continue` with the helper editor env, Abort runs `rebase --abort`, both update lifecycle and clean up reservation/session on completion; `unowned` → plain `rebase --continue`/`--abort` with a pass-through editor, no manifest/session/reservation mutation; `foreign` → Abort only, and it never mutates or deletes the owned session state (the stale manifest goes through the ambiguous-discard flow). All three side-effect contracts are tested. Refresh follows in every case.
   - **Reload reconciliation (evidence-based, conservative, repository-scoped)**: on activation, reconciliation runs **once per repository, marker-first** — read the rebase dir and its `intelligit-session` marker once, then select the matching manifest; never classify per-manifest in isolation. A retained `completed-pending-push` manifest **never claims the rebase dir** (its evidence is HEAD/branch vs `rebasedHeadOid` only), so it cannot fight a second live session over the same dir — the dir is `owned` iff the marker matches a **live** (`starting`/`running`/`paused`) manifest, and `foreign` only when no live manifest matches. Rows:
     - live (`starting`/`running`/`paused`) manifest + rebase dir → **correlate before claiming**: require the `rebase-merge/intelligit-session` marker to exist and equal that manifest's `sessionId` — the marker is written only by our sequence helper, so a terminal-started rebase can never carry it, **including an identical-input restart on the same branch, base, and original HEAD** (which passes every read-only metadata check). Then sanity-check `head-name`/`onto`/`orig-head` against the manifest. All pass → our live paused/running session: full Continue/Abort with message injection. Any mismatch → a foreign rebase is running over our stale manifest: never inject messages, never attribute the dir to our session — notice + Abort-only controls for the foreign rebase, our manifest handled as ambiguous (discard action). A stale paused manifest must never pair with a later terminal-started rebase and inject old prepared messages into overlapping commits.
     - rebase dir without manifest (terminal-started or lost state) → Continue/Abort offered; continue runs without message injection (the keyed-miss rule makes this safe).
     - manifest without rebase dir, `HEAD == expectedHead`, branch matches → rebase never happened or was aborted → delete manifest.
     - manifest without rebase dir, HEAD moved → **ambiguous, always**: an ancestor check cannot distinguish "our rebase finished while the host was unloaded" from an unrelated rewrite the user performed themselves, and a lease-valid force-push must never be armed on a misclassification. Keep the manifest, surface a one-time notice ("A rebase session did not finish cleanly — verify your branch, then push manually if intended") with a "Discard rebase session state" action. **The force-push offer is armed exclusively by the live success path the extension itself witnessed** (step 7); reconciliation never arms it. Never silently delete a `completed-pending-push` manifest.
     - **any state not matching a row above** — current branch != manifest branch (incl. the same-tip switch), detached HEAD, corrupt/truncated/unknown-version manifest, failed dir correlation — → **ambiguous by default**: notice + discard action only; never Continue with injection, never delete silently, never arm the push. The matrix is default-deny.
9. **Operation fence during rebase (scoped, enumerated)** — while a rebase (or merge) is in progress, reject with "A rebase is in progress — continue or abort it first.":
   - `dispatchCommitContextAction`: `undoCommit`, `editCommitMessage`, `squashCommits`, `dropCommit`, `interactiveRebaseFromHere`, `resetCurrentToHere`, `revertCommit`, `cherryPick`, `checkoutRevision`.
   - Branch commands: checkout/switch, merge, rebase-onto, update (fetch+merge/pull), delete, rename.
   - Read/copy actions stay available. Each fenced path gets an in-progress rejection test. A generalized typed-operation fence across all entry points is explicitly out of v1 (accepted risk, noted below).
10. **Menu enablement** — `commitMenu.tsx`: `interactiveRebaseFromHere` no longer disabled for pushed commits (still disabled for merge commits). Update the webview unit test asserting the old gating.
11. **i18n via the localization pipeline** — new strings go through the CSV source of truth (`docs/localization/localization_translation_review.csv`) with context-aware draft translations, imported via `scripts/localization-csv.js` (placeholder/codicon/plural/catalog-sync validation), then `bun run l10n:validate` + `bun run l10n:audit`. No hand-edited catalog drift.

## Key decisions & tradeoffs

- **Overlay dialog in the webviews** (not a separate editor tab, not quick-picks): PyCharm-parity modal feel; one shared component mounted in three hosts; reuses established dialog patterns. Tradeoff: constrained by panel width in the compact host.
- **Full PyCharm action set incl. drag reorder in v1** — no staged delivery of reorder.
- **Pushed commits allowed with explicit warning** (behavior change from today's unpushed-only gating) — matches PyCharm; safety moves from "blocked" to "informed consent + lease-protected push".
- **Force-push as a post-rebase toast only, pinned at both ends** — destination pinned by `--force-with-lease=<ref>:<pre-rebase-OID>`, source pinned by pushing the recorded `rebasedHeadOid` explicitly; no generic push-dialog force support.
- **Merges in range block the action** (PyCharm behavior) — no `--rebase-merges`, no silent linearization.
- **In-product Continue/Abort, no Skip** — completes the no-terminal promise; skip is niche and easy to misuse.
- **Clean-tree guard instead of autostash/auto-shelve** — predictable; avoids post-rebase stash-pop conflicts; small parity gap vs IntelliJ's auto-shelve.
- **Headless todo injection via editor-script env vars** — deterministic, quoting-safe (actions enum-validated, hashes hex-validated, messages travel through files, editor command built by one tested quoting algorithm), testable as a child process; `ELECTRON_RUN_AS_NODE` scoped to the editor command so git hooks never inherit it.
- **Host-issued one-shot requestId + origin-provider identity** — the webview expresses intent; the host owns every hash that reaches git and only the originating surface can consume its own request.
- **Keyed message map with fail-closed stop over FIFO or silent defaults** — a surprise editor invocation can never consume another commit's message, and an unresolvable message-bearing step stops the rebase loudly instead of silently discarding the user's edit.
- **Atomic reservation + in-gate recheck** — guard evaluation and process spawn form one critical section; concurrent submissions lose the reservation, not a race.

## Risks / open questions

- **Windows editor invocation** (git's sh + Electron-as-node + path normalization): covered by unit tests on the quoting algorithm and a real-sh round-trip, but real-Windows verification before release is required; CI here is macOS/Linux. This is a release gate.
- **`rebase-merge/done` format coupling**: the script parses the done-tail to key messages; format is stable across modern git, and the fail-closed rule means a format surprise stops the rebase with session preserved — never corruption, never a silently wrong message. Pin a minimum git version in docs.
- **Stale dialog state**: HEAD may move while the dialog is open; mitigated by expectedHead re-validation on submit and again inside the gate; failure message must be clear.
- **Refresh churn during a long rebase** (watchers fire per replayed commit) — existing watcher debouncing assumed sufficient; verify during implementation.
- **Accepted risk (scoped fence)**: the v1 fence covers the enumerated commit-menu and branch-command entry points; other mutation paths (SCM UI, terminal) during a paused rebase remain the user's responsibility, as today.
- **Range cap (500)** is a product constant, not config; revisit if real users hit it.

## Out of scope

- `--rebase-merges` / preserving merge topology
- Autostash or auto-shelve around the rebase
- Generic force-push support in the push flow (only the post-rebase toast)
- "Rebase onto branch" dialog (non-interactive rebase UX)
- `--update-refs`, `rebase --skip`, edit/stop-to-amend action
- Multi-select ranges (action operates on selected commit → HEAD only)
- Registering IntelliGit as the default sequence editor for terminal-initiated rebases (GitLens-style)
- A generalized typed-operation fence across every mutation entry point (v1 fences the enumerated commit-menu + branch-command paths only)
