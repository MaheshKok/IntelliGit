# Plan: Mirror the native Source Control input box into IntelliGit's commit composer (issue #155, item 4)
_Drafted by Claude from the user's ask; Shape 3 (short grill with stated defaults), reviewed by Codex in Act 2_

## Goal
Third-party AI commit-message extensions (CodeBuddy, and others that follow the same pattern) put their "generate commit message" button on VS Code's native Source Control view and write the result into the built-in Git extension's input box (`repository.inputBox.value`, exposed by `vscode.git`'s `getAPI(1)`). IntelliGit's commit composer never sees that text, so those plugins look broken inside IntelliGit. Goal: keep the native input box and IntelliGit's commit composer showing the same text, per repository, in both directions, so a message generated (or typed) in either place appears in the other.

The Git extension API has **no change event for the input box** (verified against the shipped `extensions/git/dist/main.js` in VS Code: `onDidOpenRepository`, `onDidCloseRepository`, `onDidChangeState`, nothing for `inputBox`). Native → IntelliGit therefore has to be polled; IntelliGit → native can be pushed on every draft save the host already receives.

## Approach
Numbered steps; each lands only when its gate is green. Tests first (Shape 3 → `claudex-build` loop).

1. **New module `src/views/nativeCommitInputBridge.ts`** — one small class, `NativeCommitInputBridge`, no VS Code UI code, fully unit-testable with a fake Git API and fake timers.
   1.1 Move the three `vscode.git` interfaces (`VsCodeGitExtension`, `VsCodeGitApi`, `VsCodeGitRepository`, `src/views/RefreshService.ts:42-61`) and the `normalizedPath` helper (`RefreshService.ts:339-342`, `path.resolve` + lower-case on win32) into this module and export them; `RefreshService.ts` imports them from here. Pure move, no behavior change. Reason: `RefreshService` imports `CommitPanelViewProvider`, so the provider cannot import from `RefreshService` without a cycle. `VsCodeGitRepository` gains `inputBox: { value: string }` (the shape the Git API v1 exposes).
   1.2 Constructor `{ resolveApi, readDraft, persistDraft, onNativeChange, pollIntervalMs = 1000, shared = sharedRecords }`. `readDraft: (root) => string` returns the draft currently persisted for a root (the providers' `getStoredCommitDraft`), read when needed, never cached; `persistDraft: (root, text) => void` writes the store (fire-and-forget `workspaceState.update`, errors caught and logged by the host), called by the bridge whenever it adopts native text so the store follows the box even when no webview needs telling: both providers share the same `commitDraft:<root>` keys, so an edit or clear persisted by one provider is what the other bridge pushes. `resolveApi: () => Promise<VsCodeGitApi | undefined>` defaults to: `vscode.extensions.getExtension<VsCodeGitExtension>("vscode.git")`, `undefined` when absent; `await activate()`; `undefined` when the exported object's `enabled` flag is `false` (the Git extension's `getAPI` throws while its model is disabled, so the flag is checked first and disablement is silent, not an error); else `getAPI(1)`. The resolve starts **in the constructor** (fire-and-forget), so it is normally complete long before any user action; the continuation only stores `this.api` (after a `disposed` check) and has no other side effect. A rejected resolve is logged once with `console.error("[IntelliGit] …")` and the bridge stays inert. Every public method is synchronous; nothing else in the class awaits, so `setVisible(false)`/`dispose()` cannot be overtaken by a pending tick.
   1.3 State. **One process-wide record per repository root**, `shared: Map<normalizedRoot, { base?: string; pending: boolean }>` at module scope (injectable for tests). `base` is the last value the native box and IntelliGit's persisted draft agreed on **in this session**; absent means no bridge has made contact with that root yet. `pending` means "IntelliGit's panel wrote something the box does not have yet" (a write made before first contact, or one whose native setter threw); it is repository-wide, so whichever bridge ticks first honors it. Both are shared because the native box is one object per repository per extension host; per-bridge copies were what let two bridges disagree. Per bridge, per attached root, one memo `seen: string | undefined` = the last text this bridge delivered to **its own** webview; delivery is per bridge because each webview must learn about every change, whoever adopted it. Nothing is snapshotted at attach time. Roots are keyed by `normalizedPath(root)`; a Git API repository matches a root when `normalizedPath(repository.rootUri.fsPath)` equals it. `attach(root)` registers the root (idempotent, so callers may re-attach a whole list); `detach(root)` forgets its `seen` (the shared record stays, it is still true for the other bridge).
   1.4 Reconcile, then deliver. `tick()` runs both for each attached root whose repository is found, with `native = inputBox.value`, `rec = shared.get(root)`:
       Reconcile (shared, decides what the box holds):
       - `rec` absent **or `rec.base === undefined`** (first contact this session; a placeholder record created by a pre-contact `setFromPanel` counts as first contact, not as a native change) → create the record if absent; if `rec.pending` or `native === ""` → **push**: write `readDraft(root)` into the box when it differs, `base = stored`; else → **adopt**: `base = native`, `persistDraft(root, native)`. `pending = false`.
       - `native !== base` → **adopt** (native changed since both sides agreed: a plugin wrote, or the Git extension cleared after its own commit; an empty value is a real change): `base = native`, `persistDraft(root, native)`. `pending = false`: the native change supersedes any panel write still waiting. Persisting is part of adopt, not of delivery: the store must follow the box whichever bridge adopts and whether or not this bridge's webview already shows the text (a hidden bridge's stale `seen`, or a reload's ready handshake, reads the store).
       - else if `pending` → **push** `readDraft(root)` (the host persisted the panel's text in the same handler that called `setFromPanel`, so the store is the panel's latest); on success `pending = false`.
       - else nothing.
       Push sets `base` only **after** the write succeeds; a write that throws leaves `base` and `pending` untouched, so the next tick retries instead of misreading the unchanged old native text as a native edit.
       Deliver (per bridge, decides what this bridge's webview shows; posts only, never persists): if `seen !== base` → `seen = base`, then `onNativeChange(root, base)`. This fires for a plugin write whichever bridge adopted it, for the other provider's panel edits (they moved `base` through 1.7), and once at startup with the agreed text. It never fires for this bridge's own panel writes because 1.7 sets `seen` first.
   1.5 `setVisible(visible)`: `true` starts one `setInterval(tick, pollIntervalMs)` (idempotent; runs `tick()` at once as well), `false` clears it. Visibility gates **only the poll** (native → IntelliGit); panel writes (1.7) always go through. `dispose()` = `setVisible(false)` + `disposed = true` + forget all roots.
   1.6 `tick()`: no-op until `this.api` is set. For each attached root: find the repository, skip if absent (the Git extension opens repositories asynchronously, and the first-contact rule then runs on the tick it appears); otherwise apply 1.4. Per-root `try/catch`, errors logged once, so one bad repository does not stop the others.
   1.7 `setFromPanel(root, message)`: `seen = message` (this bridge's own webview already shows it, so delivery must not bounce it back). Then, if the API is resolved, the repository is found and `shared.get(root)?.base !== undefined`: `try { if (inputBox.value !== message) inputBox.value = message; base = message } catch { pending = true; log once }`. Otherwise (API pending, repository not open yet, or first contact not made) set `pending = true` on the root's record (creating a placeholder record with no `base` if needed) and nothing else: the host has persisted `message`, and the first-contact or pending branch of 1.4 pushes it, from whichever bridge ticks first. The write is a plain property assignment; the Git extension never notifies the writer, so nothing echoes; a root that is not attached is ignored. This is what keeps a commit clear or an edit made before discovery from being overwritten by the box's restored old text, and what keeps a throwing setter from blocking the host's own persist.

2. **Host wiring, docked (`src/views/CommitPanelViewProvider.ts`).**
   2.1 One bridge per provider, created in the constructor with two host callbacks. `persistDraft = (root, text) => workspaceState.update(getCommitDraftStorageKey(runtime), text || undefined).catch(log)` (same write `saveCommitDraft` does at `:1845-1853`), fire-and-forget, called by adopt (1.4). `onNativeChange = (root, message) => postToWebview({ type: "restoreCommitDraft", repositoryRoot: root, message })` (`:466-470` already posts this shape), called by deliver (1.4). Both run inside the bridge's synchronous tick, so there is no await between reading the box, persisting, and updating the composer. The bridge never awaits the host. If the webview is not attached yet the post is dropped, which is fine: the persisted value is replayed by 2.6.
   2.2 `setRepositories` (`:385-415`): `bridge.attach(repository.root)` when a runtime is created, `bridge.detach(root)` where the runtime is deleted (`:394`). `readDraft` is `(root) => this.getStoredCommitDraft(this.runtimes.get(root))`.
   2.3 `case "saveCommitDraft"` (`:1845`): before the `workspaceState` write (no await in between), `bridge.setFromPanel(runtime.repository.root, message)`.
   2.4 `postCommitted` in `actionDepsForRuntime` (`:922-943`): when `clearCommitMessage` is true after the draft was cleared, `bridge.setFromPanel(root, "")` so the native box empties with the composer, whether or not the view is visible at that moment.
   2.5 Visibility: in `resolveWebviewView`, `bridge.setVisible(webviewView.visible)` right after the html is set, again inside the existing `onDidChangeVisibility` (`:1211`, both branches, not only the visible one), and `setVisible(false)` from the view-dispose path. `dispose()` (`:2317`) calls `bridge.dispose()`.
   2.6 Ready handshake (`handleReadyMessage`, `:1618-1622`) today restores only the active root's stored draft. Change it to post `restoreCommitDraft` for **every** runtime in `this.runtimes` (active root last, after `postRepositoryListHydration` so the webview knows the roots). Reason: a native change mirrored while the webview was detached, or into a non-active accordion row before a reload, is persisted but its post was dropped; the handshake is the replay. Same message, same reducer path, no new protocol.
   2.7 `case "getLastCommitMessage"` (`:1919-1926`) sets the composer text through `lastCommitMessage` without a `saveCommitDraft` round trip, so the bridge would never see it. After posting, call one host helper `mirrorPanelText(root, lastMsg)` = `bridge.setFromPanel(root, lastMsg)` + the same persist as 2.1, so the native box and the stored draft follow the composer. (Persisting here is a small behavior change: today a reload after loading the last message reverts the composer to the older draft; after this it keeps what the composer showed, which is what the native box shows too.)

3. **Host wiring, undocked (`src/views/UndockedViewProvider.ts`) — same touch points.** The constructor already fills `this.repositories` (`:325-328`) and activation then calls `setRepositories` with the same list (`repositoryMode.ts:784,821`), so a list diff would attach nothing: instead one private `syncBridgeRoots()` attaches every root in `this.repositories` (idempotent, 1.3) and detaches the ones that left, called at the end of the constructor and inside `setRepositories` (`:380-386`). `readDraft` is `getStoredCommitDraft(root)` (`:1993`) and `persistDraft` the matching `workspaceState.update` on the same key. `case "saveCommitDraft"` (`:1130-1141`) calls `setFromPanel` before its persist; the undocked committed path (the counterpart of `postCommitted`, found during the build) clears; `case "getLastCommitMessage"` (`:1199-1208`) mirrors like 2.7 **only if the reply is still current**: capture `this.repositorySwitchSeq` before the `await` and, when it moved, skip the **post, the mirror and the persist together** (the same guard the stash path uses at `:1274,1305`, which also returns before posting; the webview's own root check at `src/webviews/react/undocked/useUnifiedMessages.ts:249-253` cannot see an A→B→A switch back to the same root, so the host must drop the stale reply itself or the composer would show the old last message while box and store hold the newer draft, R6-#1); `onDidChangeViewState` (`:713-718`) and `open`/`dispose` (`:723`) drive `setVisible`. Undocked `restoreCommitDraft` is applied by the webview only for the selected repository (`useUnifiedMessages.ts:244-248`) and the provider already re-posts the stored draft on every selection change and on ready (`:496`, `:963`), so a non-selected repository's mirrored text is persisted by 2.1's write and shown when selected; no undocked equivalent of 2.6 is needed.
   Both providers may be alive at once (docked view + undocked panel). Two bridges then poll the same native box. That is safe: writes are idempotent (guarded by `!==`), the shared record keeps both bridges agreeing about the box, and each bridge's `seen` memo delivers every move of `base` to its own webview exactly once and never its own writes (1.4 Deliver), which is the wanted result.

4. **Webview: no change.** Both reducers already apply `restoreCommitDraft` at any time while no generation is streaming (`src/webviews/react/commit-panel/hooks/useExtensionMessages.ts:347-354`, `src/webviews/react/undocked/commitPanelState.ts:310-313`), and `RESTORE_COMMIT_DRAFT` does not re-post `saveCommitDraft`, so a native change never bounces back through 2.3. No new protocol message.

## Key decisions & tradeoffs
1. **Poll, 1 s, only while a panel is visible.** No event exists, so polling is the only native → IntelliGit path. One second is below what a user notices after clicking "generate" and costs one property read per repository per tick; nothing runs while the panel is hidden. Tradeoff: up to 1 s latency and a timer per live provider. Not a setting; a constant with a `ponytail:` comment naming the upgrade path (an event, if the Git extension ever adds one).
2. **Both directions, last writer wins, no merging.** The two boxes are the same field shown twice; the most recent edit anywhere is the truth. The shared per-root record (`base`, `pending`) is the only reconciliation state and it is what makes the two directions not fight. Tradeoff: typing in both places within the same second ends with whichever the poll sees last; accepted, nobody does that on purpose. One residual race is accepted knowingly (Round 1 #2): a `saveCommitDraft` already in flight from the webview can cross a `restoreCommitDraft` the host just posted for a native change; the composer then shows the native text while the box and the stored draft hold the composer's text, until the next edit on either side realigns them. It needs a keystroke in IntelliGit and a plugin write in the same poll interval, nothing is lost (both texts stay visible and the persisted draft matches the box), and the only fix is a protocol change, which is out of scope.
3. **Reuse `restoreCommitDraft`, no new protocol type.** The message already means "here is the draft for this root" and both reducers handle it. Tradeoff: while IntelliGit's own Copilot generation is streaming, the reducer ignores the restore (`generation.status !== "idle"`), so a native edit made during those seconds is persisted but not shown until the next native change. Accepted: the user is watching IntelliGit stream at that moment.
4. **One record per repository per process, first contact decided by who has spoken.** A plugin may have written the message before IntelliGit's panel resolved, which is the exact bug being fixed, so non-empty native text at first contact wins, unless IntelliGit's panel already wrote (committed, cleared, edited) before that first contact, in which case the panel is the newer author and its persisted text wins. VS Code restores the native box across a window reload, so "native is non-empty" alone cannot mean "someone else wrote it"; the repository-wide `pending` flag is what tells the two apart without timestamps. Accepted ambiguity: a plugin write and a panel write both landing inside the first second after activation, before the first tick, resolve in the panel's favor. After first contact both sides agree, and any later native deviation is by definition someone else's.
5. **One bridge per provider, one shared record per repository.** Sharing a whole bridge needs plumbing through `activateRepositoryMode` and a lifetime that outlives both providers; sharing only the per-root record (a module-level `Map`) costs nothing and is what makes two bridges agree about the box, while the per-bridge `seen` memo is what makes each webview still hear about every change (1.3, 1.4). Tradeoff: two timers when both surfaces are open, and a module-level map that tests must inject or reset.
6. **Types and `normalizedPath` move out of `RefreshService`** instead of being duplicated, to keep one definition of "same repository root" (Windows spelling differences are a known trap in this repo).
7. **No new setting to turn the bridge off.** The behavior matches what every other SCM-integrated extension does with the native box; a switch is speculative. Add one if a user asks.

## Risks
- The Git extension exposes `inputBox` only through the API surface, so a typing change upstream would surface as `undefined.value`; the per-root `try/catch` in `tick` turns that into a logged no-op, not a broken panel.
- Persisting on `getLastCommitMessage` (2.7) is a small deliberate behavior change to the reload path; it is called out in the CHANGELOG line.
- Multi-root workspaces: a root that the Git extension has not opened (e.g. `git.autoRepositoryDetection` off) is never found; the bridge silently does nothing for it, which is today's behavior.
- The `saveCommitDraft` path already runs on every keystroke; adding one property assignment per keystroke is negligible, but the host must not `await` the bridge there.
- `RefreshService` move: pure refactor guarded by the existing tests; the integration test that mocks `vscode.extensions` must still resolve the same extension id.

## Out of scope
- Widening IntelliGit's own "Generate" button beyond Copilot (`src/ai/commitMessageGenerator.ts:416`, `selectChatModels({ vendor: "copilot" })`); that is a separate change to IntelliGit's own generator, not to plugin compatibility.
- A user setting to disable or configure the bridge or its poll interval.
- Issue #155 item 3 (integrating project, commit, and branch cards in the full workbench).
- Any change to the webview protocol, reducers, or React components.
- Mirroring anything other than the message text (amend state, staged selection, the Git extension's own commit action).
- Reacting to the Git extension being installed, enabled, or disabled after IntelliGit activated; the API is resolved once per provider lifetime.
